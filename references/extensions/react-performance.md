# Производительность React и Next.js

Читать из [реализации интерфейса](../modules/ru-frontend-implementation.md), когда проект действительно использует React/Next.js. Сохранять существующий стек. Не переносить серверные приёмы Next.js на статический HTML, Tilda или произвольный React-проект.

## Найти узкое место

Прочитать компоненты, зависимости, маршруты, загрузку данных и правила кеша. Зафиксировать наблюдаемую проблему и подходящую меру: время загрузки, размер загружаемого кода, задержку ввода, повторные запросы или частоту дорогих рендеров. Указать условия измерения. Выбирать небольшое число приёмов под найденную причину.

## Применять по приоритету

| Приоритет | Приём | Проверка и граница |
|---|---|---|
| 1 | Запускать независимые чтения параллельно | Сохранять порядок зависимых операций, изменения данных и авторизации; ошибки обрабатывать осмысленно |
| 1 | Начинать нужный запрос раньше, ожидать ближе к месту использования | Не запускать платные или лишние запросы для ветки, которая не понадобится |
| 2 | Загружать тяжёлый редактор, график или виджет при необходимости | Проверить загрузочное состояние, ошибку и доступность; next/dynamic применять только в Next.js |
| 2 | Использовать публичный прямой импорт библиотеки, если общий импорт раздувает сборку | Подтвердить результат анализом сборки, не ломать поддерживаемый API библиотеки |
| 3 | Сократить данные между сервером и клиентом | Не передавать ключи, приватные поля и лишний сериализуемый объём |
| 3 | Устранять повторное чтение в пределах запроса; кешировать осознанно | Проверить срок, инвалидирование, пользователя и tenant; не смешивать частные данные общим кешем |
| 4 | Использовать существующий слой загрузки для дедупликации запросов | Не добавлять SWR/другую библиотеку ради единственного запроса без причины |
| 5 | Вычислять производные значения из актуальных props/state | Не хранить второе состояние с эффектом только для пересчёта суммы/имени |
| 5 | Использовать функциональное обновление при зависимости от предыдущего состояния | Проверить несколько быстрых действий и отсутствие потери обновлений |
| 5 | Применять memo/useMemo/useCallback после обнаружения дорогой работы | Не мемоизировать простые выражения автоматически; проверить зависимости и React Compiler проекта |
| 6 | Сохранить отзывчивый ввод при тяжёлом обновлении представления | Отложить именно дорогую часть, проверить актуальность результата и состояния ожидания |
| 6 | Задать размеры медиа и проверить загрузку длинных страниц | Не скрывать основной контент и не устранять предупреждение гидратации без выяснения причины |

Пример для независимых чтений:

```tsx
const [catalog, tariffs] = await Promise.all([loadCatalog(), loadTariffs()]);
```

Пример для вычисляемой суммы:

```tsx
const total = area * selectedRate;
```

Не создавать отдельные total/setTotal и эффект пересчёта, если сумма целиком определяется текущими данными. Для сохранённой сервером цены или ручного переопределения сперва установить бизнес-правило.

## Проверить изменение

Запустить существующую сборку и относящиеся проверки. Повторить исходное измерение в сравнимых условиях. Через [проверку сайта](../modules/ru-webapp-testing.md) пройти загрузку, ошибку и основной сценарий, затронутый изменением. Без измерения сообщать об исправленном механизме, не придумывать процент ускорения.

Использована выборка принципов Vercel React Best Practices; полная коллекция правил не установлена. Зафиксированные исходники: [происхождение](sources.json). Для новой версии API читать актуальные первичные документы.
