# 52. Аудит интерфейса

Русская адаптация принципов Vercel Web Interface Guidelines, v3.2.0. Основа и MIT-лицензия: [сохранённые правила](../../upstream/vercel-web-interface-guidelines/command.md). Авторские дополнения: российские форматы, приоритеты и доказательность отчёта.

## Вход и границы

Прочитать [российский контекст](../../references/ru-context.md), задачу, URL/код/макет, существующий дизайн и главное действие. Использовать известные устройства и ограничения проекта. При отсутствии объекта проверки запросить ссылку, код или скриншот одним вопросом с вариантами и собственным ответом. По скриншоту оценивать только видимое: работа кнопок, DOM, контраст без точных цветов и скорость остаются непроверенными.
Если поручен только аудит — выдать находки. Если поручены исправления или создание сайта целиком — исправить проверенные дефекты в рамках задачи и проверить затронутый путь; повторное разрешение на обычную правку не запрашивать.
Базовый дизайн уже описан в модуле 51. Здесь выполнять проверку конкретного результата, не создавать новую палитру и не повторять весь маркетинговый бриф.

## Порядок проверки

1. Обозначить область: страница/компоненты, версия, доступные материалы. При доступном интернете сверить актуальные правила с официальным источником, при работе офлайн использовать сохранённый снимок с датой. Не переносить английские правила Title Case и кавычек механически в русский текст.
2. Пройти главный путь от первого экрана до целевого действия. Найти препятствия: недоступная кнопка, перекрывающий слой, непонятный следующий шаг. Подтверждённую неисправность отличать от предположения о конверсии.
3. Проверить семантику и доступность: реальные кнопки и ссылки, подписи полей, доступные имена иконок, видимый фокус, порядок клавиатурного перехода, открытие/закрытие диалога и возврат фокуса. Сообщения состояния должны быть доступны вспомогательным технологиям; ошибка не обозначается одним цветом. Если приводишь порог стандарта, укажи актуальный критерий и способ проверки; не называй выборочный аудит сертификацией.
4. Проверить формы: назначение и автозаполнение полей, возможность вставки, ошибки рядом с полями, сохранение ввода при сбое, понятный следующий шаг. Форма не должна объявлять успех только по клику. Исполнение запросов и получение заявки проверять модулем 53.
5. Проверить адаптивность по содержимому: узкий, промежуточный и широкий экран; увеличение текста; таблицы и длинные строки; sticky-элементы и экранная клавиатура. Не скрывать существенные условия ради компактности и не маскировать дефект глобальным overflow:hidden.
6. Проверить медиа и загрузку: размеры изображений, сдвиги верстки, критическое изображение первого экрана, шрифты и fallback. Lazy loading применять к некритичным медиа ниже первого экрана. Числа скорости и Core Web Vitals сообщать только после измерения, с условиями; лабораторное измерение отличать от полевых данных.
7. Проверить движение и управление: reduced motion, прерываемость анимации, отсутствие действий только по hover/жесту. Наличие узкого скриншота не доказывает работу touch-жеста. Тёмную тему, сложные жесты и дополнительные языки проверять только если они есть в объёме продукта.

## Российский контекст проверки

- Проверить ё/й, ₽, реальные длинные заголовки и фамилии; важные названия и условия не обрезать без доступного полного текста.
- Для заданной российской локали использовать корректные рубли, десятичную запятую, группировку разрядов и неразрывный пробел между числом и единицей. Даты и время сверять с географией услуги; язык пользователя не доказывает часовой пояс.
- Для российского телефона проверить вставку и нормализацию согласованных форматов +7/8, пробелы и скобки; для международной аудитории не ограничивать ввод российским форматом. Не заявлять корректность номера по одной маске.
- Не переносить англоязычный Title Case: русские подписи писать естественно. Проверить согласование «1 заявка / 2 заявки / 5 заявок», если есть счётчики.
- Проверить, что условия согласия, стоимость и следующий шаг понятны. Актуальные правовые требования при юридическом запросе проверять отдельно; этот аудит не выдаёт правового заключения.

## Отчёт

Для каждой находки дать: ID → приоритет → место (file:line при наличии кода; иначе экран/элемент) → наблюдение → влияние на действие → минимальное исправление → способ повторной проверки.
P0 — основное действие невозможно или теряются данные; P1 — серьёзное препятствие/существенное введение в заблуждение; P2 — заметное неудобство; P3 — косметика. Учитывать контекст, не назначать всем ошибкам P0.
Объединять повторы одной причины. В начале — до 3–5 главных проблем; в конце — выполненные проверки и конкретные пробелы. Не выдумывать номера строк, метрики или рост продаж. Успешный автоматический скан не заменяет проверку человеком.

[Модуль 53](../ru-webapp-testing/SKILL.md) проверяет поведение; [модуль 54](../ru-design-polish/SKILL.md) исправляет визуальные и адаптивные дефекты. Общий список находок вести один, без повторного полного аудита на каждом этапе.
